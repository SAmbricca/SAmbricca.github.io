CASE 01

logrca: finding the incident you've already seen

Python · July to August 2026 · source on GitHub

What it does

You give it a new error. It finds past incidents that looked the same, shows how they were resolved, and drafts a root-cause note. An agent can drive the whole thing through an MCP server.

Most production errors aren't new. The same connection pool runs dry every few weeks, but the fix lives in someone's memory or in a closed ticket, and grep only finds it if you happen to use the same words.

How it works

  1. ingestCloudWatch, or a sample JSON file so it runs without AWS.
  2. normalizeTimestamps, UUIDs, IPs and numbers become placeholders, leaving a signature.
  3. groupSame signature, split into separate incidents on gaps over 5 minutes.
  4. embedall-MiniLM-L6-v2, local, 384 dimensions. No API cost.
  5. storeChroma, cosine distance. Re-indexing the same logs updates them, so nothing gets stored twice.
  6. retrieveThe new error goes through the same normalizer, then top-k search.
  7. draftA template by default. Claude if you set an API key.

The MCP server exposes four tools (query_logs, index_logs, search_similar_incidents, draft_rca) that call the same functions as the CLI. The server itself has no pipeline logic.

Measuring it

I wrote 18 queries across 12 incident types and made them hard on purpose: near-duplicates with different causes (DB pool vs Redis pool, two different out-of-memory errors) and paraphrases that share almost no words with the log line. Then I scored a keyword-overlap baseline on the same queries so the semantic numbers had something to be compared against.

18 queries, default MiniLM model. A pytest fails if semantic stops beating the baseline, so the benchmark can't quietly go stale.

The bug the eval set found

A filename like img_2231.png slipped past the number normalizer because of a regex word boundary. Two identical disk-full errors got different signatures and were filed as two incidents. Nothing crashed, so without the labeled queries I wouldn't have noticed.

Limits

  • It runs on sample log files by default. Real CloudWatch is opt-in and needs AWS credentials.
  • 18 queries is a small set and I wrote them myself, so the perfect score tells me the approach holds for these cases and little more.
  • The default drafter fills a template from the retrieved evidence. It doesn't reason about causes. The Claude backend does, and it costs money per call.

How I built it

I used Claude Code as a pair programmer, and the commit history shows it. I planned the build in stages, wrote the eval set and the keyword baseline, and I can walk through any part of the code.

Next I want a bigger eval set from real incidents and a reranking step, then to see how the numbers move.
